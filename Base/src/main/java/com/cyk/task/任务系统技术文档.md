# 自动化异步任务调度系统 (Task Scheduler) 技术文档

## 1\. 系统概述

本系统是一个基于 Spring Boot 构建的高可用、高扩展性的自动化异步任务调度模块。其主要职责是统一管理企业级自动化采集任务（包括基于 Python 脚本的 ENS 客观数据采集，以及基于大模型视觉代理的 AI 语义推断采集）。系统采用“队列排队-事件驱动-异步回调”的设计思想，有效解耦了任务的接收、分配、执行与结果处理全生命周期。

## 2\. 核心架构与设计

系统架构严格遵循单一职责与面向接口编程原则，核心组件包含以下几部分：

### 2.1 调度引擎 (`CustomTaskScheduler`)

系统的中央枢纽，负责任务的路由、状态流转与并发控制。

* **多线程池隔离**：内置 `ensExecutorPool` 和 `aiExecutorPool` 两个独立的线程池，实现不同类型任务的物理隔离，防止某一类耗时任务耗尽全局系统资源。
* **精准并发控制**：通过 `AtomicInteger` 维护各类任务的当前运行数（`ensRunningCount`、`aiRunningCount`、`specialRunningCount`），严格限制容器实例的并发上限（`MAX_CONCURRENT_TASKS`）。

### 2.2 执行器模式 (`TaskExecutor`)

采用策略模式处理多态任务。所有执行器实现 `TaskExecutor` 接口。

* **`ENSTaskExecutor`**：负责调度 Docker 环境下的 ENScan 采集进程。
* **`AITaskExecutor`**：负责调度 V1 视觉大模型代理容器执行复杂交互。
* **智能路由**：调度器支持逻辑类型映射，例如 `SPECIAL` 类型的任务在底层复用 AI 的基础设施与执行器，但可按需注入定制化 Prompt。

### 2.3 事件驱动机制 (Spring ApplicationEvent)

任务的入队与调度触发实现了完全解耦。调用方通过 `startTask` 方法将任务写入数据库及内存队列后，立即发布 `TaskEnqueuedEvent` 事件。由 `TaskSchedulerEventListener` 异步监听并触发消费者线程取任务，保证了 API 层的极速响应。

## 3\. 核心业务流程与容错机制

### 3.1 任务生命周期

1.  **创建与防重**：校验当前公司是否已存在同类型的进行中任务（PENDING/RUNNING），避免资源浪费。
2.  **入队与分配**：任务信息落盘后，存入 `TaskQueueManager`，随后通过事件触发资源分配。
3.  **鉴权绑定**：执行器在启动前，优先获取可用的账号/云配置（`AuthInfoEntity`），若无资源则抛出异常或排队等待。
4.  **异步执行与回调**：容器任务启动后立即释放 Java 线程，进入等待回调状态；当 Python/Docker 端完成后，触发回调接口进行数据解析与落盘。

### 3.2 失败退避与重试机制

系统设计了健壮的自动重试策略（最大重试次数为 3 次）：

* **部分成功保护**：若任务失败但已提取到部分有效字段，系统会暂存已收集的字段，更新目标集合后进行重试。
* **降级与换源**：重试时可动态变更指令集。例如 `ENS` 任务失败后，自动将抓取指令 (`mission`) 降级或切换为 `aqc` 等备用源；`AI`/`SPECIAL` 任务失败后，自动更改指令为“AI重试”或“特殊重试”。
* **频率限制**：内部任务入队异常时加入 2000ms 的休眠退避，防止重试风暴引发 SSH 连接激增。

## 4\. API 接口文档

### 4.1 创建异步任务

通过调用任务服务创建不同类别的自动化任务，任务会立即进入队列排队。

* **请求对象**: `CreateTaskTO`
* **关键参数说明**:

| 字段名 | 类型 | 必填 | 描述 |
| --- | --- | --- | --- |
| `companyName` | String | 是 | 目标企业名称 |
| `taskType` | String | 是 | 任务类型：`ENS` (客观数据)、`AI` (推断数据)、`OTHER`/`SPECIAL` (特殊需求) |
| `configName` | String | 是 | 绑定的云账号/鉴权配置文件名称 |
| `isUpdate` | Boolean | 是 | 是否为更新操作（覆盖旧数据） |
| `webAddress` | String | 否 | 目标网站地址（`OTHER`任务必填） |
| `fieldList` | List\<String\> | 否 | 指定需要获取的字段集合（`OTHER`任务必填） |

* **返回**: `Long` (任务 ID，用于后续追踪状态)

### 4.2 任务结果回调处理 (内部组件调用)

底层代理容器（Python/Docker）完成任务后，由控制器将结果转交回 `CustomTaskScheduler.onTaskCompleted`。

* **方法签名**: `void onTaskCompleted(Long taskId, String taskType, boolean success, Map<String, Object> result)`
* **处理逻辑**:
    1.  释放鉴权账号占用槽位。
    2.  若成功：结构化解析 JSON 结果并调用数据服务（如 `iCompaniesService`）落盘。
    3.  若失败：判定重试次数，执行状态流转（`RESTART` 或 `FAILED`）。
    4.  触发队列中的下一个等待任务 (`triggerNextTask`)。

## 5\. 使用规范与最佳实践

1.  **执行器扩展规范**：
    若需新增自动化数据源（如新增一个 RPA 代理模块），开发者应创建实现 `TaskExecutor` 接口的类，并在 `CustomTaskScheduler` 初始化或通过依赖注入的方式将其注册到 `executorMap` 中。必须保证 `start` 方法的非阻塞性。

2.  **并发与资源配置**：
    当前并发上限受 `MAX_CONCURRENT_TASKS` 以及外部 Docker 宿主机的内存/显存资源制约。调整并发数时，需同步确保 `AuthInfoService` 中的可用账号凭证数量大于或等于并发数，否则将引发频繁的“无法获取可用账号”异常。

3.  **字段映射规范**：
    系统依赖动态反射与 Hutool 工具进行数据库字段的映射 (`fillExistingBean`)。由于 Python 返回的结果通常包含嵌套 JSON 以及下划线命名法，回调入口处必须确保数据被解析为平面 `Map` 且将键转换为驼峰式命名（CamelCase），以保证自动填充的正确性。

4.  **异常阻断与事务**：
    任务的创建过程与入队操作应保持原子性。虽然 `onTaskCompleted` 会进行失败捕获，但在编写执行器代码时，严禁生吞外部异常，必须将明确的错误描述上抛，以便调度器能正确记录 `TaskLogEntity` 日志，为问题排查提供依据。
