# 知识图谱服务模块 (Knowledge Graph Service) 技术文档

## 1. 系统概述

本模块是一个基于 Spring Boot 和 Neo4j 构建的高级知识图谱服务，专为构建具有复杂上下文关系的实体网络而设计。系统集成了高维向量检索（Vector Search）功能，支持节点与关系的语义相似度计算，并实现了严格的基于 `topicId` 的会话级数据隔离。

该架构特别适用于需要维持长上下文记忆、执行复杂推理路径分析以及具有“全息有序上下文”关联需求的 AI Agent 场景。

## 2. 核心模型与架构

系统主要由以下核心数据结构支撑：

* **KnowledgeNode (知识节点)**：图谱中的基础实体，使用 `nodeId` 作为主键，包含详细文本 (`detail`)、状态 (`status`)、描述 (`description`) 以及 1536 维度的特征向量 (`embedding`)。每个节点通过 `topic_id` 进行会话绑定。
* **KnowledgeRelation (知识关联)**：节点间的有向边（类型为 `RELATED_TO`）。该关系不仅包含常规描述，还存储了“全路径上下文” (`parent_detail`)，即从根节点到当前节点的完整历史路径文本，并支持独立的边向量索引。
* **Subgraph (局部子图)**：用于表示从特定根节点出发、在指定深度范围内的局部图结构。构建过程采用广度优先搜索 (BFS)，并内置了防止环路死循环的访问记录机制。
* **TopicGraph (会话全量图)**：以 `topicId` 为界限的扁平化全局图模型，用于提取和展示单个任务会话下的所有节点和关联边。

## 3. 核心特性说明

### 3.1 带有双重重排的高级语义搜索 (Search V3 Pro)
检索系统采用了“一审召回 + 二审重排”的复合架构，以平衡查询性能与上下文精准度。
* **一审宽泛召回**：使用 0.0 阈值从 Neo4j 数据库中海选大量候选节点（默认扩大 5 倍 limit），防止潜在相关节点被遗漏。
* **二审上下文打分**：若查询时提供了上下文要求，系统将直接提取数据库中预存的入边历史向量，利用内存级纯数学计算（余弦相似度）得出上下文匹配分数。
* **最终过滤**：计算基础向量得分与上下文得分的平均值，仅保留最终平均分达到指定 `threshold` 阈值的节点，并按倒序返回。

### 3.2 全息有序上下文聚合
当建立节点间的关联 (`link`) 时，底层 Cypher 查询会自动提取源节点的所有入边历史（`parent_detail`），并与当前节点内容拼接形成新的历史路径。这使得每一条边都隐含了业务执行的完整前置步骤状态。

## 4. API 接口规范

系统提供了一套完整的 RESTful API，入口前缀均为 `/api/graph`。

### 4.1 节点管理

* **创建或更新节点**
    * **接口**: `POST /api/graph/nodes`
    * **请求体**: `KnowledgeNode` JSON 对象（需包含 `nodeId`, `topicId`, `detail` 等）
    * **说明**: 后台会检测并自动调用 Embedding 服务生成向量后存入或更新 Neo4j。
* **删除节点**
    * **接口**: `DELETE /api/graph/nodes/{nodeId}`
    * **说明**: 根据物理 `nodeId` 彻底删除该知识节点。

### 4.2 关系与图谱构建

* **创建智能关联**
    * **接口**: `POST /api/graph/links`
    * **请求体**:
        ```json
        {
          "fromId": "源节点ID",
          "toId": "目标节点ID",
          "relationLabel": "关系标签(可选，默认'Next Step')",
          "topicId": "会话ID"
        }
        ```
    * **说明**: 建立两个节点的边，并自动计算该边的上下文累积特征向量。

### 4.3 图谱查询与检索

* **获取局部子图**
    * **接口**: `GET /api/graph/subgraph`
    * **参数**: `rootId` (根节点ID, 必填), `depth` (抓取深度，默认为 3)
    * **返回**: 包含节点列表和边列表的 `Subgraph` 对象。
* **获取完整会话图谱**
    * **接口**: `GET /api/graph/topic/{topicId}`
    * **说明**: 抓取该特定 `topicId` 下构建的完整业务拓扑图。
* **高级语义搜索**
    * **接口**: `GET /api/graph/search/advanced`
    * **参数**:
        * `query` (必填): 搜索关键词
        * `context` (选填): 用于二审重排的期望上下文文本
        * `limit` (选填): 返回最大数量，默认 5
        * `threshold` (选填): 过滤阈值，默认 0.7
* **测试文本相似度**
    * **接口**: `GET /api/graph/test-similarity`
    * **参数**: `t1`, `t2` (对比文本)
    * **返回**: 两端文本的计算向量相似度及评级报告。

## 5. 使用规范与最佳实践

1.  **环境初始化限制**：
    * 系统在启动时 (`@PostConstruct`) 会自动执行 Cypher 语句检查并创建名为 `vector_index` 和 `relation_vector_index` 的向量索引。
    * **强依赖**：使用的向量模型（如 DashScope/Milvus 等）输出维度**必须固定为 1536 维**，否则与 Neo4j 索引配置冲突，引发运行错误。
2.  **查询深度控制**：
    * 在底层图谱关系遍历时（如深层图查找），Repository 层设定了 `[*0..10]` 的绝对安全上限。
    * 调用子图查询或路径计算时，应合理评估 `depth` 参数，避免引起内存溢出或全图爆炸。
3.  **数据隔离原则 (Topic Management)**：
    * 所有 `MERGE` 与 `MATCH` 的写入/查询操作均深度绑定了 `topic_id` 属性。
    * 在上层应用中，严禁在未传递或混用 `topicId` 的情况下执行节点写入与关联，以确保不同会话的推理记忆链路互不干扰。
4.  **性能优化考量**：
    * 在执行高级搜索时，系统大量复用了存入数据库中的旧特征向量以规避实时的 Embedding API 网络调用。因此，在直接操作数据库时，切勿手动清空或破坏节点的 `embedding` 属性，以免破坏检索稳定性。
